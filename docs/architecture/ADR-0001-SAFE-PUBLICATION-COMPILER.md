# ADR-0001 从发布门禁改为安全发布编译器

## 1. 状态

已接受

## 2. 背景

v1 的 `managed-publish` 复制原工作树、运行验证、创建候选 Commit，再调用 `gate`；它没有调用 `prepare` 或 `apply_replacements`

`apply_replacements` 只处理可解码文本；路径、引用、数据库、图片、PDF、Office、Git 历史和二进制没有对应转换器

这些实现会在真正困难的风险出现时停止发布，却不会生成安全替代候选，因此产品行为与用户的发布目标相反

## 3. 决定

v2 采用安全发布编译器架构；安全发现成为修复规划器的输入，候选在隔离目录中持续变化，功能验证和独立复扫通过后获得认证，发布器随后写入精确候选

## 4. 后果

正面结果包括以下内容：

- 私有源保持不变
- 新项目不会携带私有历史
- 无法证明安全的对象被重建、剔除或替代
- 候选安全与功能状态分别获得证据
- 认证完成后能够继续普通发布

代价包括以下内容：

- 工具需要多类型转换器、引用修复器和功能合同
- 验证不可信项目代码需要操作系统级隔离
- 重大功能降级、法律状态和所有权问题仍需要信息所有者决定
- 自动认证只能证明固定策略和工具覆盖，不能证明绝对零遗漏

## 5. 被放弃方案

- 只扩大 `allow_with_risk` 会让未解决安全问题进入公开候选，因此不采用
- 只把 `deny` 改名不会改变主流程，因此不采用
- 继续让用户手工处理全部 Finding 无法实现自动安全发布，因此不采用
- 新项目继续复制私有历史会保留旧凭据和私人元数据，因此不采用
