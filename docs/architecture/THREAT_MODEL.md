# GitHub 安全发布编译器 v2 威胁模型

## 1. 保护目标

系统保护以下对象：

- 源项目中的凭据、私人身份、真实数据和私有基础设施
- 私有 Git 历史、LFS 实体、子模块目标和发行附件
- 私有策略、原始候选、检查点、签名密钥和发布身份
- 候选功能完整性、认证完整性和远端对象一致性
- 第三方许可证、版权、署名和来源链

攻击者只需让一个不安全对象进入公开候选，或让发布器写入一个未经认证的对象，就能破坏保护目标

## 2. 信任边界

全部源项目内容都按不可信输入处理，包括代码、测试、构建脚本、Git Hook、子模块、归档、文档宏和二进制

系统分成以下信任域：

- 检测器只读源快照，不持有 GitHub 写凭据
- 转换器只写隔离候选，不持有 GitHub 写凭据
- 验证器在无凭据、默认断网的隔离环境中执行项目代码
- 认证器只读取脱敏后的候选摘要和验证证据，使用受操作系统保护的签名密钥
- 发布器只读取认证候选、授权记录和目标绑定，不执行项目代码，也不读取私人原值

这种分离让恶意项目代码无法直接取得发布身份

## 3. 主要攻击路径

### 3.1. 内容逃逸

- 真实凭据包含占位符子字符串，旧规则把整个值误判成示例
- 测试路径自动降低秘密严重度，真实测试凭据被当成合成数据
- 同一 Git Blob 出现在多个路径，扫描器只保留一个较安全的路径语境
- 私人值经过 Unicode 相似字符、零宽字符、编码或归档嵌套后逃过检测
- 超大对象在大小检查前整体读入，造成内存耗尽或扫描中断
- 正则表达式出现灾难性回溯，拖垮整次审计

### 3.2. 网络和依赖攻击

- GitHub Pages 或远程附件重定向到回环、私有网络、云元数据地址或非常用端口
- 域名在解析和连接之间改变地址，绕过服务器端请求伪造防护
- 缓存的 Gitleaks 二进制被替换，旧实现只信任缓存路径
- 依赖下载阶段把未验证文件提供给验证器

### 3.3. 执行隔离攻击

- 项目验证继承 GitHub、SSH、云端或私人环境变量
- 项目代码访问宿主文件系统、Docker Socket、网络或提权能力
- 多进程解析被误当成安全沙箱，但子进程仍继承宿主权限
- 私有目录权限收紧失败后继续写入候选原文

### 3.4. 认证和发布攻击

- 验证结束后候选 Tree 发生变化，认证仍引用验证前对象
- Pull Request 合并没有绑定已审计 Head SHA，分支被替换后仍然合并
- 发布重试创建第二个提交、标签或 Release
- 发布器接受策略、工具、目标或授权已经变化的旧认证
- Release 附件来自另一批次，远端 Tree 与认证 Tree 不一致

### 3.5. 法律和所有权攻击

- 自动替换 LICENSE、NOTICE、CITATION、版权或第三方署名
- 权利不明的必要组件被静默剔除，实际功能发生重大变化
- 风险接受记录被用于绕过私人内容修复

## 4. 固定防护

- 精确占位符语法替代子字符串判断
- 路径只提供语境，不能单独降低凭据严重度
- 每个 Git Blob 保留全部可达路径语境
- 文件、Blob、LFS、下载和附件使用有界流式读取
- 私有正则只接受受限语法，并在独立时间片内执行
- 每次使用缓存扫描器都重新核对锁定摘要
- 每次重定向、解析和连接都核对协议、主机、端口与 IP
- 验证器移除全部发布凭据，并在数值型非 Root 用户、断网、只读根文件系统、只读候选挂载和受限资源的容器中运行项目代码
- 容器隔离不可用时进入 `needs_input`，验证器不得使用普通本机进程继续执行
- 旧深度扫描收据只复用精确绑定的覆盖结果，不能压低高可信凭据或 Policy v4 私人实体
- 验证完成后重新计算 Commit、Tree、Index 和 Patch
- Pull Request 合并绑定精确 Head SHA
- 所有批准证据绑定对象摘要、策略摘要、扫描器集合、签发者、签发时间、到期时间和复审条件
- 发布器只接受签名认证和仍有效的精确授权记录
- 公开变更摘要只保存动作计数，删除说明使用通用公开名称，不复制原始私有路径或值摘要

## 5. 已知边界

自动检测无法证明绝对零遗漏；未知格式、加密对象和无法解释的二进制不能进入候选

已经公开的凭据需要先撤销或轮换；历史重写不能收回 Fork、缓存和旧克隆中的副本 [1]

Docker 客户端存在不代表隔离环境已经可用；容器引擎、网络封锁、只读挂载和逃逸金丝雀全部通过后，验证器才能执行不可信项目代码
